# Contributing Guide

Thank you for contributing!

The goal of this project is **not** to become the largest system design repository.

The goal is to become the most practical, concise, and interview-focused guide for backend engineers.

---

# Core Principles

## 1. Be Interview Focused

Every section should help someone perform better in a backend system design interview.

If it doesn't, leave it out.

---

## 2. Explain Decisions

Don't just define technologies.

Explain:

- Why they exist
- When to use them
- When not to use them
- Their trade-offs

---

## 3. Keep It Concise

Readers should be able to finish a topic in 5–10 minutes.

Avoid unnecessary theory.

---

## 4. Prefer Diagrams

If a diagram explains something better than a paragraph, use the diagram.

---

## 5. Use Original Content

Do not copy:

- Books
- Blog posts
- Course material
- Slides
- Diagrams

All explanations and diagrams should be original.

---

## 6. Stay Vendor Neutral

AWS examples are welcome.

Azure and GCP equivalents are also encouraged.

Avoid suggesting there is only one correct cloud provider.

---

## 7. Use Real Engineering Trade-offs

Avoid statements like:

❌ Redis is always faster.

Instead explain:

✅ Redis reduces latency but introduces cache invalidation and operational complexity.

---

## 8. Keep a Consistent Structure

Every topic should follow the Topic Template.

Consistency improves readability.

---

## 9. Cite Official References

When adding references, prefer:

- RFCs
- Official documentation
- Academic papers
- Engineering blogs from the technology creators

Avoid low-quality or AI-generated sources.

---

## 10. Optimize for Learning

Always ask:

> "Will this help someone explain the concept confidently in an interview?"

If the answer is no, rewrite it.

---

# Style Guide

- Use active voice.
- Keep paragraphs short.
- Prefer bullets over long prose.
- Use diagrams whenever possible.
- Keep jargon to a minimum.
- Explain acronyms on first use.
